# AGENTS.md — PgBackRust

Authoritative operating manual for ANY agent (human or AI) working on this repository.
Read this file fully before touching code. Re-read it when starting a new session.

## 1. Project identity

PgBackRust is a from-scratch Rust rewrite of [pgBackRest](https://github.com/pgbackrest/pgbackrest)
(PostgreSQL backup and restore). It is NOT a C port. It is a clean-room implementation
in Rust that reproduces pgBackRest behavior one-for-one.

Strategy: **Option B. Full byte-level compatibility.**

- PgBackRust must READ every repository artifact that pgBackRest has ever written.
- PgBackRust must WRITE artifacts that pgBackRest >= 2.59.x reads without error.
- Both binaries may share the same repository during migration.
- The upstream mirror lives at `/root/pgbackrest` (full clone. origin = pgbackrest/pgbackrest).
  It is the reference implementation and the source of golden artifacts.

## 2. The Iron Rules (non-negotiable. every commit. no exceptions)

### R1. Never break read compatibility
Every repo written by any pgBackRest version must restore with PgBackRust. This is the
product promise. A feature is not "done" until it can consume old-version artifacts.

### R2. Never break write compatibility
Everything PgBackRust writes (manifest. info files. WAL segments. encrypted data.
compressed data) must be parseable by the reference pgBackRest binary. Prove it with a
round-trip test that runs the REAL upstream binary on PgBackRust output. No exception
for "nobody uses that". Compatibility is the product.

### R3. One-for-one feature parity
Every feature in the upstream feature ledger (see docs/FEATURE_PARITY.md) must exist in
PgBackRust with identical behavior. No feature is dropped. No feature is silently
altered. New features outside the ledger require explicit user approval first.

### R4. Golden-file testing
Every ported module is verified against golden artifacts generated by the real pgBackRest
binary (from /root/pgbackrest). Golden files are committed. Regeneration is a deliberate
act with a diff review. Fuzz inputs come from upstream test/fuzz.

### R5. No behavior drift
Default option values. CLI syntax. exit codes. error codes and messages. log format.
lock behavior. file permissions. fsync guarantees. All identical to upstream unless the
user approved a deviation. Deviations are listed in docs/COMPATIBILITY_CONTRACT.md
section "Approved deviations" (currently empty).

### R6. No performance regressions
Baseline benchmarks exist per command (docs/COMPATIBILITY_CONTRACT.md section
"Performance baselines"). A change that regresses any baseline by more than 5% is
rejected unless the user approves. The rewrite must match or beat upstream on:
backup throughput. restore throughput. WAL archive latency. memory footprint.

### R7. unsafe discipline
The workspace denies unsafe by default (cargo deny / lints). unsafe is allowed only in
designated crates and each unsafe block carries a justification comment. Soundness
reasoning must be written next to the code.

### R8. Dependency minimalism
Dependencies are chosen to match upstream's zero-dependency philosophy. Prefer std.
Prefer small audited crates. Every new dependency is justified in the Cargo.toml
comment or PR body. No async runtime unless approved (sync-first design. upstream is
synchronous and this is a deliberate match).

## 3. Architecture decisions (binding)

- **Sync-first.** Upstream is synchronous and fork-based. PgBackRust uses threads for
  local parallelism and processes for remote roles. No async runtime until approved.
- **Workspace layout.** One crate per upstream module group (see FEATURE_PARITY.md
  mapping). Crate names mirror C module boundaries so the C-to-Rust map stays 1:1.
- **Errors.** thiserror + a generated error-code table matching upstream error codes.
  Stack traces on every failure like upstream.
- **Types.** Rust std types everywhere. serde for JSON/XML serialization of info files.
  Custom pack codec crate for protocol wire format. The pack format must stay a faithful
  reimplementation (no serde shortcut that changes bytes).
- **Config.** Declarative schema ported from upstream build/config.yaml. Codegen at
  build time. Option names. defaults. dependencies. groups. validation. identical.
- **Compression.** IO filter trait matching upstream filter chains. gz. bz2. lz4. zstd.
  Defaults identical to upstream (check current defaults at port time).
- **Crypto.** cipherBlock format (AES-256-CBC + HMAC key derivation) is a HARD
  compatibility surface. Do not modernize it. Implement it byte-identically.
- **No .c.inc emulation.** Upstream uses .c.inc include-twice files. Rust expresses this
  with generics and modules. Do not copy the pattern.
- **No memContext emulation.** Upstream manual memory trees become scoped lifetimes and
  arena patterns. Do not build an Rc/RefCell mimicry layer.

## 4. Definition of Done (every feature)

1. Feature ported to Rust (or stubbed with explicit TODO + tracker entry when blocked)
2. Unit tests in the crate (Rust-native. not C translations where avoidable)
3. Golden parity test passes against real upstream binary output (both directions)
4. Compatibility round-trip passes: old artifact -> PgBackRust and PgBackRust artifact -> upstream
5. Baseline benchmark recorded and not regressed
6. FEATURE_PARITY.md status updated
7. Commit message follows the convention (see section 6)

A feature is DONE only when all seven items are true.

## 5. Workflow rules

- TDD: failing test first. then implementation. then refactor.
- Small commits. One logical change per commit.
- Never commit generated golden files without stating how they were produced.
- Never "fix" upstream behavior because it looks wrong. It is the spec. File a
  deviation proposal to the user instead.
- When porting a module: read the C source IN FULL first. Read its tests too
  (test/src/module/*). The tests are the unwritten spec.
- Assumptions must be written down. If the C code is ambiguous. document the choice in
  the crate docs and flag it in the PR.
- Diagnostic report before any structural change. Version files. Approval required for:
  architecture changes. dependency additions. deviations from upstream behavior.

## 6. Commit conventions

```
<type>(<crate>): <imperative summary>

- parity: what C behavior this reproduces (file + function refs into /root/pgbackrest)
- compat: which products of compatibility this touches (read/write/round-trip)
- verify: exact commands run and results
- perf: benchmark delta vs baseline (if applicable)
```

Types: feat. fix. test. perf. docs. chore. Ports are ALWAYS feat commits (never
"rewrite" or "refactor").

## 7. The upstream sync duty (PERMANENT. runs forever)

PgBackRest development never stops. Neither does ours.

Every day the sync job (scripts/upstream-sync.sh) fetches upstream and compares the
upstream tip against the commit recorded in .upstream/state.json. For each new upstream
commit it maps touched C files to PgBackRust crates via .upstream/modules.json and
classifies the impact. The report lands in .upstream/reports/. The user reviews and
approves actions.

When an upstream change touches a PORTED crate:

- Port the change into the matching crate
- Re-run golden parity tests (BOTH directions)
- Re-run the affected command benchmarks
- Verify no compatibility regression. Commit as a normal port commit
- Do it promptly. Drift is the enemy. See docs/UPSTREAM_SYNC.md

When an upstream change touches a NOT-YET-PORTED crate:

- Log the impact in FEATURE_PARITY.md
- No code action. The port will absorb the change when it happens

The sync job never commits. Never pushes. Never merges. It reports. The agent ports.
The user approves.

## 9. Anti-patterns (never)

- Copying C code into Rust line by line. Translate intent. not text.
- Importing C files with bindgen as a shortcut. Clean reimplementation only.
- Modernizing formats "while we're at it". Format changes require user approval.
- Using upstream as a black box. Read the C. Read the tests. Ask why.
- Claiming a feature done without the round-trip test. See section 4.
- Letting the sync report pile up unreviewed. Act or escalate.
